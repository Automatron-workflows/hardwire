## LinkedIn draft

I built Hardwire around a simple question: before an agent calls an action,
how do we make its inputs, effects and approval requirements explicit?

The demo shows sign in, an invoice payment and a setting change. Then you can
try the actual validator against local examples. Change the invoice amount or
send the wrong type and the request is rejected.

The smallest developer experiment takes one saved HTML form. Hardwire generates
a draft contract, checks a valid and invalid input, and produces an MCP tool
description. No app or API key needed.

The desktop bundle also exposes the inspection tools to compatible MCP hosts.
Application handlers, authentication and real approvals remain your responsibility.

I am looking for the first five developers willing to try a form and tell me
where it becomes confusing or fails. Synthetic examples are welcome.

Try it: https://automatron-workflows.github.io/hardwire/experiment.html
Code: https://github.com/Automatron-workflows/hardwire

## Show HN draft

Title: Show HN: Hardwire, inspect agent action contracts from saved HTML forms

I built a small MIT toolkit for describing and checking actions before connecting
them to an agent. It infers draft contracts from static HTML, validates inputs
and declared approval floors, generates MCP tool descriptions and checks trace
consistency. The desktop bundle exposes five local inspection tools.

The demo uses sign in, invoice payment and settings. Those are local fixtures,
not real Google or payment integrations. The first command starts with the
settings form and shows a boolean passing and a string being rejected.

I would particularly welcome forms where inference is wrong and feedback on
whether the resulting contract saves any integration work. The current corpus
is only three synthetic examples. I have not established real website accuracy
or performance gains.

## Distribution sequence

1. Verify the public release and MCP Registry entry. Link to the exact download.
2. Personally invite five developers who build agent or application integrations.
3. Observe each first attempt. Fix the first repeated blocker before expanding.
4. Share the film and working task in one relevant public channel. Answer replies.
5. Publish what outside users found, with their permission. Credit contributions.
6. Expand to another channel after the previous cohort produces useful results.

For the first cohort, record completion without help, first confusing step,
client and version, useful output, repeat use and contribution. Keep personal
recruitment notes private. Public issue counts and package downloads are not
unique users; automated CI can inflate downloads and clones.

At a hypothetical 5% visitor to star conversion, 1,000 stars requires 20,000
repository visitors and 2,000 requires 40,000. Those are planning assumptions,
not benchmarks. If five relevant developers cannot find useful value, improve
the task before seeking that scale of exposure.

The first evidence goals are five independent completions, three returning users
and three outside contributions. A high star count is a stretch outcome. Do not
buy stars, coordinate votes or claim adoption from the project's own test runs.
